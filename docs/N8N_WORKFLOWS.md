# n8n workflows

Files (importable exports, n8n 2.43.3):

* [`n8n/workflows/workflow-a-loan-discovery.json`](../n8n/workflows/workflow-a-loan-discovery.json)
* [`n8n/workflows/workflow-b-user-matching.json`](../n8n/workflows/workflow-b-user-matching.json)
* [`n8n/workflows/workflow-c-notification.json`](../n8n/workflows/workflow-c-notification.json)

They are generated by [`n8n/build_workflows.py`](../n8n/build_workflows.py). Edit the generator and re-run `python n8n/build_workflows.py` instead of hand-editing JSON. The workflows contain **no secrets**; they reference four credentials by fixed id:

| Credential id | Name | Type | Used by |
|---|---|---|---|
| `LoanEngInternal1` | Loan Engine Internal API (X-Internal-Token) | Header Auth | every call to `/internal/*` |
| `LoanEngWebhook01` | Loan Engine Webhook Token (X-Webhook-Token) | Header Auth | B and C webhook triggers, B→C call |
| `LoanEngMailpit01` | Local Mailpit SMTP | SMTP (`mailpit:1025`, no TLS) | C, smtp mode |
| `LoanEngAwsSes001` | AWS SES sender | AWS | C, ses mode (cloud only) |

## Import (automated)

```bash
docker compose up -d --build
python scripts/setup_n8n.py
```

The script reads tokens from `.env`, streams them into the container (they are never written into the repo), imports the credentials and the three workflows, publishes them and restarts n8n. It is safe to re-run. Add `AWS_SES_ACCESS_KEY_ID`, `AWS_SES_SECRET_ACCESS_KEY` and `AWS_SES_REGION` to `.env` before running it if you want the SES credential created too.

## Import (manual, through the UI)

1. Open http://localhost:5678 and create the owner account (local only).
2. **Credentials → Add credential → Header Auth**: name `Loan Engine Internal API (X-Internal-Token)`, header name `X-Internal-Token`, value = `INTERNAL_API_TOKEN` from `.env`. Repeat for `Loan Engine Webhook Token (X-Webhook-Token)` with header `X-Webhook-Token` and value `N8N_WEBHOOK_TOKEN`.
3. Add an **SMTP** credential: host `mailpit`, port `1025`, SSL off, no user/password.
4. **Workflows → Import from file** for each JSON file. Open each HTTP/Webhook/Email node and select the matching credential if n8n doesn't link it automatically (ids differ when created in the UI).
5. Publish (activate) B and C (webhooks) and A (schedule).

## Workflow A – loan product discovery

`Run manually` / `Weekly schedule (Mon 06:00 Asia/Kolkata)` → `Get configured sources` → `One item per source` → `Loop over sources` (one at a time) → `Fetch robots.txt` → `Evaluate robots.txt` (backend, RFC 9309 rules; unreachable or forbidden robots.txt ⇒ don't crawl) → `Fetch product page` (fixed User-Agent, 20 s timeout, never throws) → `Extract, validate and upsert` (backend) → `Polite delay` (5 s) → loop. When the loop is done: `Flag stale products` → `Run summary`.

* Sources: [`backend/config/loan_sources.json`](../backend/config/loan_sources.json) (ICICI Bank, Axis Bank, Kotak Mahindra Bank personal-loan pages; robots.txt allowed these paths on 2026-10-10 and is re-checked every run). HDFC Bank was considered but its robots.txt returned 403, so it is excluded.
* Extraction is deterministic regex over visible text. Every value keeps a note with the snippet it came from (`loan_products.extraction_notes`). When a page lists several values (e.g. per segment), the strictest is stored and noted.
* No LLM is used in A.
* Failure handling: a non-2xx response, a timeout, or fewer than 2 extracted fields (a layout change) is recorded as a crawl failure. Existing data is never deleted or overwritten. After 3 consecutive failures or 7 days without verification, a product is flagged `is_stale`. After 30 days unverified it is set `is_active=false` (not deleted).
* Manual demo: open the workflow and click **Execute workflow**, or run from the CLI:
  `docker compose exec -e N8N_RUNNERS_BROKER_PORT=5690 -e N8N_PORT=5699 n8n n8n execute --id=LoanEngWorkflowA`
  (the extra ports avoid clashing with the running n8n process).

Real result from 2026-10-10 is in [`test-results/workflow-a-live-run-2026-10-10.txt`](test-results/workflow-a-live-run-2026-10-10.txt).

## Workflow B – user matching

`Upload completed webhook` (POST `/webhook/loan-matching`, Header Auth `X-Webhook-Token`, responds immediately) → `Validate payload` (UUID only) → `Get upload batch` → `Batch ready?` (else `Stop: batch not ready`) → `Stage 0 - normalize ambiguous product criteria (optional LLM)` → `Stages 1-3 - SQL pre-filter, deterministic evaluation, persist` → `Optimization summary` → `Trigger notification workflow`.

* All HTTP nodes retry 3 times with a 3 s wait. Matching is idempotent per batch (unique `(user, product, batch)` and a per-batch advisory lock), so retries and duplicate webhook deliveries are safe. A concurrent run gets HTTP 409.
* Details and numbers: [OPTIMIZATION.md](OPTIMIZATION.md).

## Workflow C – notifications

`Matching completed webhook` (POST `/webhook/loan-notify`, Header Auth) → `Validate payload` → `Prepare grouped outbox` (backend creates or claims one log row per user; already-sent rows are never returned) → `One item per message` → `Send one at a time` loop → `Dry run?` / `SES mode?` → `Send via AWS SES` or `Send via SMTP (Mailpit)` (error output enabled) → `Record ... SENT` / `Record ... FAILED` / `Record DRY_RUN` → `Throttle (1 msg/s)` → loop. When done: `Finalize batch notification status`.

* Mode comes from the backend's `NOTIFICATION_MODE` (`dry_run` / `smtp` / `ses`), so n8n has a single source of truth.
* Every message is addressed to `NOTIFICATION_TEST_RECIPIENT`. The intended user appears only as `user_id` plus a masked address inside the body.
* Failed messages are **not retried automatically**. They are re-sent the next time C runs for that batch (max `NOTIFICATION_MAX_ATTEMPTS`=3, then `GAVE_UP`). Trigger that with `POST /internal/batches/{id}/trigger-matching`, which re-runs B and then C; already-delivered rows are skipped. A claimed-but-unreported message becomes reclaimable after 10 minutes.
* If a re-run of B changes a user's match set before delivery, the old undelivered row is marked `SUPERSEDED` (never sent) and the new match set gets its own row, so the user receives one current email rather than two.
* Dry run records `DRY_RUN`, never `SENT`.

## Hosting modes

| Setting | Local (default) | Cloud (n8n on EC2) |
|---|---|---|
| `N8N_HOST` | `localhost` | the instance's DNS name or `localhost` behind an SSH tunnel |
| `WEBHOOK_URL` | `http://localhost:5678/` | URL that **the backend** can reach, e.g. `http://<private-ip>:5678/` |
| `N8N_EDITOR_BASE_URL` | `http://localhost:5678/` | where you open the editor (SSH tunnel recommended) |
| `LOAN_API_BASE_URL` | `http://api:8000` (compose service name) | the HTTP API URL from `serverless deploy` |
| Backend → n8n | `http://n8n:5678/webhook/loan-matching` | `http://<n8n-private-ip>:5678/webhook/loan-matching` (SSM param) |

No public HTTPS endpoint or domain is needed: the only inbound caller of n8n webhooks is the backend (inside the VPC or compose network), and no OAuth providers are used. If you ever need public HTTPS for a demo, a temporary tunnel (`cloudflared tunnel --url http://localhost:5678`) works. Its URL changes on every start, so it is unsuitable as a permanent callback and must be re-entered in `WEBHOOK_URL` and the backend config each time.
